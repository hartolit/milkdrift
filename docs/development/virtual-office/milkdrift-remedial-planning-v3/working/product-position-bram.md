Ada's product position or a coordinator-selected product alternative. I read the independent
intakes/trial, actual cross-examination, Cyra's fresh-read corrections, current source and API

it is not an independently approved product design. No implementation or new runtime test was
performed for this position.

## Complete outcome model

The product helps a person turn a goal into inspectable work, keep the useful method, and run it
again with different inputs. The person chooses an owner and receives available operations under
their authority. They can start with a goal, a saved definition or manual composition. A goal is
input to an authorized operation or existing method; it does not itself create permission or a
hidden workflow. A proposed plan is inspectable before it becomes an immutable accepted revision.

A definition has responsibilities, decisions, input/result contracts, dependencies and permitted
adaptation. A run retains the accepted evidence and exact revisions that governed it. A future
change may add investigation or repair while completed facts remain visible. The reliable-use
case fixes obligations that internal adaptation cannot erase. If a reviewer discovers those
obligations are wrong, the product makes the disagreement and new authorization boundary visible;
it does not report removing a verifier as successful ordinary repair.

The same person may reuse an exact method, make an independent editable definition where its
identity permits, or call a public service. The source and authority selected for each persist
after acceptance. A readable definition on B is not automatically a local child of A. Copying an
identity-bound governed method can refuse. A private service does not become editable because its
call appears collapsed. These are the actual P1/r2 qualifications.

Capabilities let the person or method request tools, external models, direct operations or
cooperation from other hosts. A client connection is an observation/control route, not a peer
trust relationship. Execution-only hosts remain useful. A remote task keeps a workflow origin
where the current adapter requires it; direct client→B must not be advertised as an unsupported
C→B relay. Managed installations supply enduring tools/files/services; stopping the UI or a task
does not remove them. Learning compares declared evidence and can conclude failure or uncertainty
before any separately authorized promotion.

The interface should explain this as **work, results, and permitted change**, with owner and
authority visible where they affect a decision. It need not make everyone learn every internal
noun. It must nevertheless expose the distinction when an action would change rights, lineage,
accepted work or an external resource.

## Three serious alternatives

**C — retain executable owners; improve authoring and inspection.** Keep the current typed task
and structured control model, but add complete daemon-owned authoring conveniences where an
operator otherwise assembles several mutually dependent mutations. Present a synchronized graph
and structured outline, with standards-informed symbols and explicit Milkdrift semantics. Shared
discovery plus concrete committing actions follows P1/r2; direct routes remain available. Current
source already supports generic mutation submission, so no new backend abstraction is justified
merely by wanting a new toolbar. This has the smallest semantic migration and the risk of
preserving accidental restrictions under better labels.

**R — make structured work regions the canonical authoring model.** A method contains nested
sequence, choice, parallel, repetition, wait and call regions with explicit entry/result contracts.
Authoring a parallel region specifies its branches, completion condition and result construction
together; graph edges become a derived view. This is a credible structural replacement because
it can eliminate invalid half-authored fork/join ownership and repeated port/edge coordination.
Its cost is potentially losing valid current graphs, needing a versioned region-to-execution
mapping, migrating all API/CLI/agent inputs and retaining accepted old history exactly. A region
model must still express cross-region data selection, child calls, signal scope and authorized
future adaptation. It cannot win by rejecting a hard graph that current users legitimately need.

**S — adopt one standard's executable subset as the definition contract.** Select either UML
Activity semantics or a BPMN executable subset and provide explicit extensions for authority,
exact pins, uncertain effects and prospective changes. This could make authoring and interchange
more predictable for standards users and external tooling. It requires independent agreement on
token activation, merge/join behavior, data readiness, cancellation, loop timing and extension
round trips. Similar glyphs cannot substitute for that mapping. S is a plausible strategic option
if standards interoperability is desired; U08 alone establishes a principles preference, not
that costly interchange promise. Mixing whichever UML/BPMN behavior is convenient is not S.

## Concepts must earn their place

`Task` is an external capability request, not an instruction-only node. `Branch` chooses one path;
its current port-key priority is a meaningful cost that a standards-shaped diamond can conceal.
`Fork` owns isolated branches; `Join` decides when progress is permitted; `Reducer` constructs a
value. A human “parallel review then compose” interaction can set all three together without
claiming that synchronization itself generated an accepted answer. C should offer that complete
edit only after the source proves the generated mutation batch has one owner and is not duplicated
in Svelte. R earns its strongest case here.

`Wait` and `SignalWait` both suspend progress, but their waking evidence differs and survives
restart differently. They can share a form shell, not a misleading wake-up rule. `Repeat` reuses
a pinned body under hard bounds rather than creating an arbitrary cycle. `Subworkflow` is a
versioned call with child obligations. `Terminal` declares a scoped outcome, not proof that every
remote effect has disappeared. Removing these distinctions would move rather than remove their
obligations.

Context selection, immutable artifacts and managed writable areas concern different lifetimes.
One generic “memory” object would obscure who can see inputs, mutate working files or retain
results. Budget reservations and usage observations likewise cannot become UI estimates.
Evaluation and promotion are distinct because evidence may be negative or incomplete. Their
combined user journey can be concise without making comparison itself publish a winner.

Bounds need owner-specific justification. UI windowing can be configurable; protocol document
limits, artifact ceilings and accepted budget obligations cannot be raised by an interface
preference. Finding a small hardcoded example does not establish that the domain needs a global
mode or unlimited resource. Discriminating work should identify a valid denied operation and
trace why the bound exists before changing it.

## My selected recommendation for comparison

I favor C for the first complete production implementation program, with **R retained as a
serious replacement trigger**, not a ceremonial rejected option. There is substantial observed
value in existing ownership/recovery and a demonstrated browser boundary gap, while no available
case yet proves those owners obstruct the reviewed outcomes. C must include advanced connected
work and human review early; otherwise it cannot discover the evidence that would justify R.
I would favor R if multiple valid structured edits require users or the frontend to coordinate
duplicated structural rules that a daemon convenience cannot express coherently, or if S28 cannot
change its review process within intelligible authority boundaries. That decision requires a
complete region translation/migration experiment, not merely fewer boxes.

S should guide the notation profile now, with normative semantics compared honestly. I would
promote S to an executable replacement if the user selects interchange with actual external
consumers, or if independently tested normative mappings substantially improve expression and
comprehension enough to justify migration. “Models know BPMN” cannot supply that evidence.

All three must face S21 (child/service/resource hold/grant change), S26 (continuous repair/tool
development/reuse), S28 (the investigation changes its own process) and S29 (diagram/outline/
machine-input/daemon round trip). Their predictions differ most at region editing, unfamiliar
control semantics and active-work migration. A successful two-step run cannot select a winner.

The implementation proposal may proceed under C as a **conditional technical recommendation**,
retaining outcome coverage and a reopening checkpoint. It may not quietly make “keep the enum”
an enduring user requirement or mark R/S impossible. No meaningful behavior retirement or lowered
protection is selected by this position.
