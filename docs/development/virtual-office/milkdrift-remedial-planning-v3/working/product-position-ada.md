# Ada: independent product-model position

Revision Ada-P2/1, 2026-10-10. I wrote this after reading G1/r1, P1/r2 and the actual trial/fresh-read
corrections, and before reading Bram's product position or a coordinator product selection. It
uses the reviewed [working goals](vision-baseline.md) and [trial](review-method-trial.md), not an
assumption that the current vision or all preserved seed features are unquestionably right.

## A complete outcome model

My proposed product explanation is **work with an inspectable plan, accepted obligations and a
retained record**. A person may begin with a goal, an existing plan or a direct tool operation.
An agent may propose work from that goal. The person can inspect and edit a proposal before the
owning daemon accepts a definition; explicit authority can preauthorize bounded proposals and
future changes. Definitions say what should happen. Accepted occurrences record what did happen.
Neither a chat message, canvas movement nor network connection changes those facts on its own.

An accepted run binds supplied inputs and an exact starting definition. The operator can follow
progress, inspect permitted context and outputs, and distinguish an observed failure from a
missing observation. If a capability disappears or authority narrows, the run offers an honest
reason and permitted recovery actions. A fresh browser can recover the same accepted work by its
owner and identity. A lost reply never authorizes a new effect under a fresh request key.

The same model supports exploratory repair and dependable results. An agent may investigate and
replace future implementation work within an accepted allowance. It may not redefine the required
evidence, target or verifier to pass its own candidate. Changing this run, changing a reusable
definition, publishing a different agreement and improving the tools are separate consequential
actions even if one actor has permission for all of them. Preauthorization is useful because it
removes repetitive human decisions inside known limits, not because it removes those limits.

Reuse is an exact reference at its workflow owner, or an independent copy where source visibility
and identity rules permit it. A service offers a public callable contract while keeping internal
rights with its owner. Remote execution places an authorized operation on a host; it does not
move the workflow or require publication. P1/r2 adds essential eligibility facts: a readable remote
revision is not automatically locally stored, governed copies can refuse, execution-only hosts do
not acquire workflow services, and role removal must settle live obligations.

Tools and services may outlive the operation that prepared them. Editing ownership and deletion
rights remain explicit. A workflow's artifact is not the same thing as a live working directory
or a deployed service. Selected knowledge can support a new method candidate; an independent
evaluation can reject it, remain inconclusive or support a prospective promotion. Promotion affects
eligible future use, never accepted executions. A failed candidate remains useful evidence.

The living diagram is an executable explanation, not necessarily the only starting interaction.
Goal entry, an action table, and direct graph editing should expose the same validated definition.
The graph must show data, decision and concurrency meaning when it matters. An operator should
not have to draw every policy mechanism, but hiding a mechanism cannot hide its consequences.

## Complete alternatives

**Conservative: expose the current owners directly.** Keep present blueprint/node/publication
semantics and create production authoring and inspection routes for each. This is strong where
source already has difficult recovery and authority behavior. It minimizes semantic migration
and makes advanced mechanisms reachable. Its failure mode is an implementation-shaped product:
the operator must translate intent into several administrative nouns and manually connect steps
the application could express as one meaningful edit. It also cannot draw standard constructs
whose activation the current runtime does not provide.

**Structural reinterpretation: intent-led interactions over explicit accepted operations.** Group
work by the operator's immediate purpose—prepare, perform, inspect, change future work, reuse,
offer a service, improve a method—while preserving exact identities and committing actions.
Offer a shared discovery route with distinct P1/r2 consequences. A compound compositor editor
can combine selecting a wait policy and a result operation; the saved graph still has one owner
for each. New or changed semantics enter the daemon only where a complete journey proves a gap.
This is my preferred planning candidate because it can simplify decisions without discarding
working behavior. Its cost is proving every compound gesture produces the same meaning across
graph, table, CLI/API and agent authoring; otherwise it merely creates a second hidden workflow
system in the client.

**Standard-informed executable model: choose a bounded UML Activity or BPMN basis and translate
the product onto it.** Treat standard semantics as the executable contract for a declared subset,
with explicit extensions or replacements for Milkdrift authority and durability. This is a credible
larger alternative if expressive gaps are systemic or useful interoperability requires it.
It can supply disciplined merge/event/call behavior and familiar concepts. It costs a full semantic
compatibility account for definitions, active work, receipts, revisions, clients and effects;
familiar symbols do not prove that migration. A declared supported subset can be coherent, but
using standards only to rename current constructs would not be this alternative.

My preferred candidate can use standard-grounded notation without claiming to implement the third
alternative. The distinction must stay visible. If modeling the demanding cases repeatedly needs
ad-hoc restrictions, the conservative executable core should be challenged more deeply rather
than protected by a widening set of visual exceptions.

## Value, gain and loss across V01–V12

structural reinterpretation with the conservative route; the final column names what a standards
replacement would additionally have to prove.

| V01 usable operations | Intent-led forms and action tables reduce manual document assembly; a compound editor can become misleading. | Preserve every permitted public operation and actionable refusal in the new authoring path. |

| V03 adaptive future work | Unified prospective-change review exposes allowed repair; hidden contract edits are a risk. | Preserve accepted old occurrences, protected agreement and uncertain work during semantic migration. |

## Discriminating cases and current concerns

S28, the review itself, is the strongest combined case: independent reviewers receive bounded
sources; opposing proposals are retained; a fresh source discovery changes only the affected
future work; the accepted result can be used on another product; and a bad candidate remains
recorded. All alternatives must show useful progress without granting a reviewer power to rewrite
the acceptance conditions. An interface that only reruns a fixed prompt list does not satisfy it.

S21/S26 add independent resource and service lifetimes. A repair agent's allowed code change
must not imply permission to replace its verifier or destroy a shared installation. Selecting a
different host must preserve who accepted and can resolve the old operation. These cases protect
the real value behind existing mechanisms while permitting a better representation.

The standards comparison identified a concrete open activation concern. In
[predecessors_ready](../../../../../crates/runtime/src/engine/support.rs), a normal target needs
every incoming control edge's source to have succeeded and selected that edge; Join is the special
fork-owned exception. There is no Merge NodeKind. A plain exclusive branch whose alternatives
reconverge on one continuation therefore appears unable to activate that continuation. This is a
source-modeled concern, not an executed defect report; validator acceptance and an ordinary
consumer reproduction must be established. None of the alternatives may hide it with a diamond.
The complete options are a supported equivalent construction, a relevant daemon merge extension
with compatibility/evidence, or an explicit authoring refusal with a stated product cost.

Subsequent source refinement, 2026-10-10: the validator explicitly rejects multiple incoming
control edges except on a fork-owned Join (`validation.rs`, `validate_control_topology`). This
narrows the concern to an authoring limitation, not an accepted-but-stalled graph. Encapsulating
the choice in a pinned child with separate terminals is a credible current construction to compare
against a merge extension; its extra identity/context/edit boundary must be accounted for. The
coordinator owns the isolated production-library probe and any executed evidence.

## Dependencies and reversal

This position requires G1/r1 and P1/r2; it informs product selection, notation, frontend actions
and adoption. It does not select browser packaging, a new schema, a new scheduler or universal
publication. Another independent reviewer should challenge the combined candidate, especially
whether a hidden compound edit demands knowledge the UI claims to remove.

I would prefer the conservative route if the task-led interaction cannot keep exact meaning
visible through permission changes and reconnect. I would prefer the larger standard-informed
runtime alternative if independently modeled user cases expose repeated unfixable activation or
composition limits and a complete migration preserves the valued authority/recovery behavior.
Word count, enum count and source familiarity do not choose among these alternatives.

## Actual comparison with Bram — 2026-10-10

After preserving Ada-P2/1 I read [Bram BP1](product-position-bram.md). Much of my intent-led
reinterpretation and Bram's improved current-owner route is the same candidate at different
levels of explanation. Pretending that difference is architectural opposition would weaken the
review. Bram's canonical structured-regions alternative is a more substantial replacement than
my interaction grouping: the saved definition itself changes, so graph edges become a projection
and migration is mandatory.

The exclusive-convergence refusal is one concrete reason the improved-current-owner route cannot
be purely cosmetic. I recommend a complete bounded choice extension inside that route, while
comparing a canonical choice region with paired graph nodes at its owning boundary. That is less
disruptive than changing every definition to regions and more honest than hiding a new child
workflow under a merge glyph. If additional meaningful cases require repeated paired structures
that the daemon cannot author coherently, Bram's larger region replacement becomes stronger.
The choice remedy must preserve data selection and live-change scope; a control-only diamond is
not a complete answer to “choose an approach, then review its result.”
