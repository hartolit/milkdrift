## Findings and challenges

**BR1-01 — exact integer handling is an unassigned executable prerequisite unless P01 names it.**
The protocol carries `u64` guards/generations/sequences, whereas ordinary JavaScript JSON parsing
can round them. F2 now chooses lossless parsing/serialization with boundary cases, but P01's generic
“strict decoding” could be interpreted as ordinary JSON plus TypeScript assertions. Add explicit
exact-integer contract tests to P01 and P09's changed-contract audit. This is not an argument for
changing server counters to strings without a protocol decision. A browser can otherwise display
the correct-looking work yet serialize a different expected guard or request, undermining the
very recovery model A1 preserves.

**BR1-02 — R-C01 must permit a useful future edit inside a selected arm, not only after the merge.**
NP1's initial after-selection wording could be implemented as a whole-region freeze. P04 now says
not to blanket-ban future repair, but its positive example emphasizes an unentered future reviewer.
Require a selected arm with A1 completed and A2 unentered: replace A2 while preserving the selected
route, already consumed inputs and compatible merged-output contract. Also refuse arm switching,
data escape and output-schema rewrite after consumption. This discriminates a bounded adaptive
choice from merely adding a terminal converger. I sent this to Ada before her revision. A same-scope
region that prevents normal adaptive investigation would lose value compared with the explicit
child alternative, even if the simple choice probe passes.

**BR1-03 — count a satisfied join separately from a successful composed result.** NP1 correctly
distinguishes Any completion, First success and reducer First in configured order. Its frontend
consumer must retain those distinctions in collapsed and low-zoom views. With A failed first and
B canceled before producing output, Any may be satisfied while result construction has no acceptable
data. A green composite badge derived only from the join misrepresents the result. Add this negative
data-readiness case beside B-fastest/A-first-order. Use an accessible textual policy/result status;
two tiny visually similar diamonds cannot carry ordered choice versus merge meaning by shape alone.

**BR1-04 — declare the supported static hosting topology.** Cyra directly raised this finding;
my own cross-check agrees F2's exact `connect-src` policy qualifies F1's Add connection. The selected
deployment is a user/operator-hosted static application with an approved endpoint set, plus each
daemon's explicit origin configuration. A generic public website where anyone types arbitrary
private endpoints is not yet qualified. The UI must diagnose an origin outside the deployed policy
and explain which operator setting is needed. P01 must test the actual release CSP and remote HTTPS
route, not count localhost Chromium+CORS alone as the multi-host result. If this makes real onboarding
unusable, fixed-target same-origin proxy is a live alternative rather than an architecture failure
that the user must work around silently.

**BR1-05 — storage bounds must not obscure a permitted stop.** Cyra raised the full-store case after
reading F2. Preserve all unknown requests, but reserve finite control-request capacity or make exact
export/authorized native cancellation a clear escape when ordinary capacity is full. A disabled
Cancel button with only “quota exceeded” would contradict the useful-recovery outcome. This is a
client storage allocation issue, not permission to submit unrecorded effects or erase unknowns.

**BR1-06 — changed-grant recovery needs operation-specific wording.** Ada reported this risk and
the source supports it: native saved-run replay compares exact authority; command identity/fingerprint
binds the original grant. Current authorized run reads can recover a known accepted run under a
different grant, but no generic command-receipt lookup has been established. A denied/missing read
is not proof that an old start was never accepted. P02 should say “inspect the known object where
currently authorized, or exact replay only under the required original binding”; changed authority
can leave a genuinely unresolved request. F2 must use the same language and no auto-unlock/migration.

## New discriminating variation: very large guard and lost response

Before implementation, fix the following oracle independently of the chosen parser. A Rust-produced
fixture supplies a legal exact guard `9007199254740993` and a distinct neighbor `9007199254740992`.
The author reads the former, prepares an authorized guarded command, closes the browser after the
owner accepts it but before the response is processed, then imports/reopens the exact saved record
under the same owner/actor/grant. The command body must retain the former numeric token, and exact
replay must return the same durable result. A later deliberately changed neighbor under the old ID
must conflict; an imported record must not send merely because it was opened. Test this through
the real daemon public consumer with a Rust fixture that legitimately establishes the boundary,
not a mocked success response or billions of actual operations.

If the selected fixture cannot naturally create that guard, keep the exact wire round-trip as a
contract test and choose another legal public `u64` field for an actual command. Report the split
evidence honestly. This variation targets producer/consumer numeric equivalence; UI screenshots,
normal small sequences and Rust-only idempotency tests would miss it.

## Final source correction — BR3, 2026-10-10

A further end-to-end read found an inaccurate current-behavior assumption in my F1 and A1/P02's
concurrent-author wording. [Authoring base](../../../../../apps/daemon/src/host/commands/authoring.rs)
compares `request.expected_revision` to `draft.base_revision`, then reads that exact immutable
revision. `finish` calls [retain_revision](../../../../../apps/daemon/src/host/commands/definitions.rs),
which uses [RedbStore::put_revision](../../../../../adapters/redb-store/src/revision.rs). The latter
checks exact immutable identity and valid ancestry before inserting; it does not compare a mutable
workflow head. Therefore two valid descendants of the same base may both be saved. Another author's
save does not automatically make the old immutable base a conflict.

F1/F2/FE1 now distinguish actual envelope/base mismatch from divergent accepted revisions. The
interface must show ancestry and selected exact revision, allowing deliberate comparison or
construction from a chosen base; it cannot silently make a projected latest item a semantic head.
Active-run sequence/adoption and presentation-layout generation guards remain real and different.
I sent the correction to Rowan/Cyra for A1/P02 and dependent recheck. This is source-traced evidence,
not an executed concurrency test. Add a positive two-author/same-base sibling-save test as well as
a true guard-mismatch refusal. A mutable shared editing head would require a separately justified
public owner; no such new mechanism is selected merely to preserve erroneous wording.
