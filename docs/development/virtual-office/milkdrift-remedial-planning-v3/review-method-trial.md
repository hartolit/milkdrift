# Exercise the review method on one real question

**Purpose:** find out whether the process can distinguish facts from interpretations, revise a consequential premise and carry the consequences forward. A well-written instruction is not evidence that this will happen.

Run this during 02 using evidence recovered in 01. It is the first substantive vision/product decision, not a parallel artificial project or an excuse to delay all useful work. Record results in `working/review-method-trial.md` and the real debate in its whiteboard topic.

## Choose a question with actual consequences

A suitable candidate is: **which needs underlie reuse, restricted service invocation and execution on another machine, and which of those needs are genuinely separate?** The user both proposed and questioned relationships here. Existing source provides behavior to inspect, so competing explanations can be tested against something concrete.

Do not mandate separation, unification or publication as the answer. Another question may be selected if it is at least as consequential and has conflicting or ambiguous primary grounds. State why it tests the review rather than merely the agents' ability to restate an obvious constraint.

## Define what will count before debating

Keep a short assessment record:

- Can reviewers locate and distinguish original intent, their interpretation and source behavior?
- Do they identify whether disagreement concerns a fact, a scope, a mechanism or a user preference?
- Can they describe a successful user path and an interruption/permission case without adding an unexamined premise?
- Do proposed alternatives make different predictions or expose an explicit product tradeoff?
- Can a fresh reader reconstruct the recommendation and its strongest objection from the record?
- Can a changed premise lead to a correct, limited list of decisions that need reconsideration?

These are observable checks, not a numerical “coherence score.” Passing does not mean choosing the coordinator's favored design or finding a defect. Defending the existing arrangement against contrary cases is a legitimate result.

## Perform the actual investigation

1. **Independent intake.** A primary-source reader explains the need from original user excerpts/history. A source investigator explains actual public behavior and limitations. Keep their initial accounts separate from this package's outcome synthesis and the coordinator's preferred synthesis; record what context each saw.
2. **Disagreement.** Compare the accounts. Identify an assumption that changes the answer. Preserve both the strongest current-design defense and a credible alternative. Do not manufacture another option for numerical variety.
3. **Grounds.** Trace load-bearing references to original evidence. If two documents merely repeat the same claim, count that dependency once. Establish whether the disputed “requirement” is an instruction, speculation, an agent inference or current implementation behavior.
4. **Discriminating case.** Write competing predictions before any test. Use the narrowest safe existing public path or a clearly modeled scenario. Record source/env/results, or why execution was unavailable. Do not replace real permission or recovery decisions with fixtures.
5. **Actual conclusion.** Revise or defend the proposal. Explain retained value, loss, new obligations, uncertainty and the parts that require a user choice. A changed label without a changed dependency or user action is not necessarily a remedy.
6. **Fresh-context read.** Give the record and source links to an actual new reader who did not author them. Ask them to explain the choice, the rejected alternative, the strongest objection and dependent design work. They may disagree; this is not a recall test requiring the preferred answer. Necessary oral clarifications become maintained context.
7. **Labeled premise-change exercise.** In a separate exercise section, hypothetically alter a meaningful premise: for example, the caller gains or loses permission to inspect internals, or the destination is an execution-only host. Ask which conclusions would change and which still follow. Mark the premise hypothetical and do not pollute the live record or report a source defect from it.

No private chain-of-thought is required. Retain public reasoning, source anchors, predictions, results and decisions sufficient for review.

## Examine how the process performed

It has not passed merely because everyone wrote a report. Correct the procedure/context if a material case shows:

- a tentative user example treated as a hard requirement;
- an agent summary mistaken for an independent source;
- contrary evidence mentioned but ignored without a defense;
- a hybrid adopted without checking the combined behavior;
- a revised premise with unchanged dependent claims;
- a fresh reader unable to establish what is recommended or why;
- a preferred answer imposed despite a legitimate user tradeoff.

Repair the affected part of the packet or review procedure and repeat only the failed checks. Do not restart the whole investigation, and do not demand endless consensus. If independent sessions or required observation access are unavailable, record which checks remain unperformed. The final package must carry that qualification; the coordinator cannot manufacture an independent pass.

## Gate for scaling the review

02 may rely on the method for dependent design recommendations only when the trial establishes a readable evidence-to-decision path and a meaningful dependency check, or explicitly scopes which claims remain conditional because proof is unavailable. A known failure to distinguish intent from assumption must be corrected before it is multiplied across the project.

Record the actual procedure change, if any. Do not infer a universal law of model reliability from one case. Carry this case into the wider system comparisons and S28, rather than maintaining a disconnected showcase that never influences the implementation plan.
