# A production workbench for inspectable, adaptable work

**F1/r4 and F2/r4** select a maintained standalone Svelte application that consumes the canonical
structured source in [NP3](notation-profile.md), ongoing work in
[Elin's WorkCommitment proposal](../working/agent-directed-work.md#u18-disposition-one-continuous-work-commitment-in-the-existing-controller-owner),
and the user's [U17/U18 product directions](../intent-source-excerpts.md#u17--human-reviewed-knowledge-and-precise-evidence).
These are implementation proposals. The user approved the product directions, not these particular
owners or a finished application. There is no human usability pass or positive release-browser
qualification from writing this specification.

The application has four connected destinations: **Work** for goals, commitments, methods, drafts,
runs and future changes; **Operations** for direct tools and public services; **Resources** for
enduring installations and their editing/lifecycle obligations; **Improve** for selected knowledge,
assessments, declared comparisons and explicit reuse/adoption. Owner, actor and freshness remain
visible. Common discovery helps find useful work, while committing actions distinguish exact
reference, independent copy and public invocation. A public service remains useful when its
implementation is private; inspection never invents an editable private graph.

The person chooses intended outcomes, permitted operations/resources, model preferences, total
allowance, acceptance obligations, independence requirements and when intervention is required.
They do not have to assemble ports, select an account ID or operate receipt plumbing to begin
ordinary work. Advanced inspection can explain the exact identities and effects that support a
decision. Natural-language instructions do not grant authority or silently widen those choices.

## One editable method source through every client

P01 must first deliver the complete source/validation/lowering/runtime/public-authoring boundary.
The P02 workbench then uses `WorkflowProgram` and complete `ProgramEditBatch` operations for
Sequence, ordered Conditional with clause results, Parallel and its completion/results policy,
bounded Repeat, pinned Call, Await, Return, tasks and typed value sources. Diagram, accessible
outline, forms, Rust client/API and agent input submit the same canonical operations. The browser
owns layout and unfinished drafts; it owns no independent workflow compiler or second editable
graph. It displays the daemon's validated result and path-specific diagnostics.

Conditional priority is explicit ordered business meaning: first matching clause, then a distinct
default. IDs remain stable when clauses move or are renamed. Data binding names its source once;
rendered data/control lines project that source. Parallel completion and usable result availability
have distinct labels. An external synthesis is an ordinary task with full capability/context policy
and exact selected result/outcome bindings. A first-success result can coexist with an uncertain
losing writer; a green logical result cannot hide that writer's hold or reservation.

Saved definitions remain immutable, with valid sibling revisions from concurrent authors. The UI
shows ancestry and the selected revision; it invents neither a mutable global head nor automatic
conflict on every sibling save. Run adoption, layout and envelope guards retain their own actual
refusals. Unknown executable constructs are read-only with the original document preserved; saving
a reduced document after dropping unknown fields is forbidden.

| Existing source or action | Visible result and available next action |
| --- | --- |
| Open an old graph revision | Exact historical source and execution view, including old port-key branch precedence. Existing execution, replay and authorized reuse continue through the legacy reader into the same checked execution plan. No silent conversion on open. |
| Edit an old graph | Request `PrepareProgramConversion`; review a new source revision, preserved order/results/ownership and origin. The server validates semantic correspondence before offering a save/adopt action. |
| Conversion cannot preserve a relationship | Name the exact crossing, control/data relationship, result or ownership rule that prevents conversion; retain the old source unchanged and exportable. Offer continuing/reusing the old revision or creating separate new work with explicitly selected evidence. Do not offer a lossy save or hidden permanent legacy writer. |
| Adopt converted or edited source into a paused run | Show exact revision/frontier/sequence basis, retained completed results, selected clause and pending changes. Active leaves/calls/waits and uncertain effects retain their governing plan. Pause is not proof of physical stop. |
| Incompatible or stale adoption | Preserve the candidate and report the changed selected clause, active reparenting, consumed input, result contract, protected agreement or stale sequence. Refresh/reassess under a new reviewed request; never replay old intent with silently updated guards. |

This is a consequential compatibility choice: unrestricted editing of every old accepted graph is
not established. Unconvertible graphs remain readable, executable, replayable and reusable; their
region conversion/edit refuses. If preserving arbitrary old graph editing is mandatory, NP3's
smaller graph correction alternative must be reconsidered. A successful conversion demonstration
cannot erase this limit. [The comparison and dissent](../working/structure-comparison.md).

This qualification does not allow refusing all old edits. The required P01 compatibility corpus
includes current model-editor and prompt-sequence methods, old parallel/pinned calls and permitted
Task-only repair in a managed protected root. The UI must support those converted methods and
show successful allowed pending repair under the original agreement. Blueprint derives the exact
legacy agreement view from checked source/plan plus its origin correspondence; neither the UI nor
a copied fingerprint may bless altered protected behavior. Unsupported arbitrary graph shapes
remain a separate compatibility limit, not a reason to omit these positive journeys.

## Ongoing work is an inspectable commitment

The selected proposal places `WorkCommitment` in `control::controller::commitment`. Control owns
accepted next-action intent; runtime remains the execution owner. Ordinary model, critic, work and
evaluation methods use the same authoring and runtime operations as manually initiated work.
The workbench consumes this owner through the same public commands as the Rust client and agents.
Closing the tab, switching hosts or losing a stream stops observation, not authorized coordination.

| Person's action or situation | Public owner interaction and inspectable consequence |
| --- | --- |
| Begin with a goal | Review exact input/evidence selection, success obligations, allowed capabilities/resources, cumulative budget, round/no-progress/deadline bounds, criticism and intervention policy. `CreateWorkCommitment` accepts that policy with an exact recoverable request; it does not treat an absent model response as an empty method. |
| Inspect continuing work | `InspectWorkCommitment` shows goal/policy, current assessment, linked method revisions and associated runs, accepted rationale/evidence, disagreement, remaining/reserved/uncertain allowance, pending actions and stopping reason. Each run/result links to its actual owner. A projected phase is not proof of execution success. |
| Add criticism | `SubmitCriticism` binds the selected artifact and expected commitment version. Show it as a claim awaiting assessment, with source/relationship, rather than a command or established fact. Permitted outcomes include retaining the original result with reasons, investigation, prospective revision, escalation or stop. |
| Answer or approve | `AnswerClarification` targets the exact outstanding question/version. Approval of a consequential candidate uses the ordinary scoped proposal/approval path. Neither elapsed time nor a different round's answer grants permission. |
| Review prospective change | Present source diff, affected future work, exact selected evidence, preserved completed work, expected guards and approvals. Ordinary proposal/approval/apply/resume operations remain distinct accepted facts even when preauthorized policy continues them automatically. |
| Pause, resume or stop | Commitment pause/resume/cancel commands control future admission. Show affected associated work and actual cancellation progress; expose authorized uncertainty resolution separately. The proposed persistent gate blocks future local durable entry acceptance when paused/closed/expired; an effect admitted before closure may physically begin afterward. Accepted reporting and settlement continue. Remote work already admitted follows its own cancellation/uncertainty contract; a local pause does not prove it stopped. Resume requires current authority and remaining allowance. |
| Reach a bound or repeat without progress | Display the exact exhausted round/time/budget/no-progress rule, retained failed/rejected decisions and permitted escalation. A new context, retry, child run or revision cannot reset the commitment allowance. |
| Change future requirements | `AmendCommitmentPolicy` presents an immutable successor, expected version/frontier and explicit action carry-forward. It closes admission at a new gate generation; affected future actions need fresh authorization. Old command/authority bases stay exact, used/reserved/uncertain totals remain, and the account cannot be topped up/reset. Widened rights require separately authorized future work; a protected agreement change needs a distinct agreement/run. |
| Lose a reply or restart | Recover the exact request and inspect the durable commitment/action associations. Pending internal commands retain exact material before effects; the browser never regenerates a model response or runs a local supervisor to repair missing status. |

The UI distinguishes planning, working, waiting for an answer/approval, paused, stopping, completed
and stopped coordination from the statuses of its associated runs. It can show a useful result
while unsettled work remains prominent. Private service internals retain separate authority and
allowance; an outer commitment handle does not confer internal read/control. The ordinary user
sets budgets and rights; the owner creates account associations from accepted actions.

Manual operation and a one-round commitment remain supported. Automatic reconsideration means
preauthorized assessment and continuation, not automatic agreement with every critic. The strongest
alternative makes an asynchronous supervisor an ordinary runtime root, which would make supervision
itself reusable/editable but requires new nonterminal child observation and lifetime semantics.
The selected closed coordination policy does not promise that full programmability.

## Knowledge, evaluation and adoption remain distinct

Improve can start with a research artifact, architectural lesson, explanation or decision without
inventing an executable method, managed installation or service generation. The shared learning
owner introduces `LearningSubject::{Knowledge, ExecutableMethod}`, exact source selection,
`AssessmentDeclaration`, `RecordAssessment`, comparison and separate knowledge-reuse approval.
Existing protected-method qualification retains its stronger verifier/publication obligations.
[U17 representation and migration](../working/agent-directed-work.md#u17-disposition-evaluated-knowledge-without-invented-executable-methods).

The evaluation form records exact inputs and compared versions/outputs, criteria, authenticated
reviewer/authority, judgment, reasons, limitations and counterevidence. It permits a single result
assessed against a criterion or a comparison. Controlled assessments show the preaccepted criterion
and reserved role basis; retrospective assessments are visibly **retrospective**. Self-review is
allowed when the declaration permits it and visibly labeled **author review**. Known shared sources,
participation and unknown independence remain visible; multiple favorable reviewers are not labeled
independent merely because their names differ.

Human judgment, agent judgment and automated verification have distinct badges and explanations.
A favorable human assessment establishes a scoped preference or acceptance, not universal
improvement or a passed technical check. Negative, failed, missing and inconclusive results remain
findable. A declared independence requirement refuses an ineligible reviewer; a retrospective
record cannot be relabeled controlled. Mandatory verification and protected-effect checks remain
mandatory. The browser cannot mint a trusted verifier receipt from an uploaded assessment.

`ApproveKnowledgeForReuse` is a separate authorized action on the exact item/version and its
applicability/limits. It makes that item eligible for selected reuse; it does not replace a method,
change a running commitment, or publish a service. Later fresh-context selection carries the
lesson's limitations and counterevidence, not only its favorable summary. Method adoption and
publication retain their separate exact operations and authority.

## Browser, custody and engineering contract retained

The [prior detailed interface tables](../working/production-interface.md) and
[engineering contract](../working/frontend-engineering.md) retain useful layout, operation/recovery,
resource and browser annotations. They describe r3; this r4 supersedes their graph-source/R-C01,
finite goal-planning/R-FE02, method-only learning and old phase assignments. Those old remedy names
must not be implemented as parallel owners beside NP3/WorkCommitment/U17. Their preserved browser,
resource/public-invocation and accessibility requirements apply where compatible with this revision.

The maintained app is `apps/workbench`, a static Svelte client. The r3 SvelteKit/Svelte/TypeScript,
Node/npm, Svelte Flow and other package versions are candidate inputs, not a compatibility result.
P02 verifies current primary documentation, resolves compatible exact versions and commits the full
lock. Svelte Flow is conditional on complete complex-region rendering and accessible editing;
native controls and a complete outline/form path are required. No Node production runtime or
private browser compiler is implied. The [practice proposal](frontend-practice-proposal.md) adds
reusable rules; canonical practice files/selector remain unchanged by this planning assignment.

| Contract | Required behavior and consequence |
| --- | --- |
| Deployment | Operator/user-hosted static build with approved endpoint set in CSP, exact daemon CORS origin and remote TLS termination retaining loopback daemon binding. Test the actual release origin topology. Same-origin fixed-target proxy remains a credible alternative; arbitrary-endpoint public hosting is unqualified. |
| Credential custody | Bearer stays in tab memory; reload reprovisions it. Authenticated identity reads send it before stable-host comparison, so trusted origin/TLS governs that first delivery. Persistent login/native vault requires a separate design. |
| Private local retention | Explicit personal-profile IndexedDB mode is unencrypted at rest. Session/export mode keeps drafts in memory and requires completed exact export before effects. Logout clears bearer/authorized views and locks retained recovery records; it does not cancel backend work. |
| Exact effect recovery | Freeze exact identity/body/guards/original authority before send. Block sends on failed durable storage/export. Lost replies retain the original command; current reads and exact replay have different permissions. Direct-serving recovery may use current Inspect and stored original basis where its owner permits; do not impose workflow-specific replay rules universally. |
| Bounded recovery | Initial client proposal: 128 records/32 MiB total, with 16 records/4 MiB reserved for control. Never evict pending/unknown requests. Full capacity offers exact export or an authorized native control route; no unrecorded emergency-send bypass. Clearing browser data can destroy its only local locator. |
| Wire precision | Bound bytes/depth/arrays before decoding; validate runtime shapes. Exact lossless integers, nested values, IDs and guards survive `2^53`, protocol extrema, persistence/export/replay. `Response.json()` plus a cast cannot restore rounded digits. Unknown executable meanings remain read-only. |
| Observation | Bind reads to endpoint/stable host/actor/grant/epoch; clear authorized caches on changes. Finite frames/queues, last fully handled cursor and explicit resync preserve durable-run versus process-local capability/health distinctions. A complete empty snapshot replaces the projection. |
| Rendering and tests | Preserve supplied SVG, visible focus and state labels; colors/density require rendered checks. Keyboard, non-drag pointer, screen reader, zoom/reflow, forced colors and reduced motion cover the actual app. Rust-owned real-daemon fixtures, strict type/contract tests, static release browser tests and named topology/device bounds qualify behavior; mocks alone do not. |

## Delivery order and evidence

P01 delivers canonical source and the public/runtime owner end to end, including legacy lowering,
conversion/refusal and prospective repair. P02 folds browser foundation into the first retained
connected Svelte slice: connect, author a complete small structured method, save, run, inspect and
reuse it with another input. Its first real human checkpoint follows that delivery, before advanced
screens dominate the program. P04 adds continuous WorkCommitment interaction and authorized
reconsideration; P07 adds knowledge/assessment/reuse; P08 tests combined work. The
[implementation program](proposed-implementation/README.md) owns exact assignments and gates.

P02 must include source reload/outline/diagram agreement, overlapping predicates with stable
priority after renaming, a legacy conversion refusal, immutable sibling saves, real stale guards,
changed authority, lost response and storage pressure. The human should predict which next action
will run and why, without learning internal account/port taxonomies. P04 must show criticism
retained as a claim, reasoned acceptance or rejection, positive pending-work repair, exhausted/no-
progress stopping, browser/daemon restart and actual unsettled effects during cancellation. P07
must show nonexecutable knowledge, controlled and retrospective assessment, allowed self-review,
required-independence refusal, negative evidence and separate reuse/publication authority.

P08 combines multiple owners, private service use, managed-resource obligations, future repair,
independent criticism, cumulative allowance, uncertainty and a retained adverse assessment in one
work commitment. A polished happy path or reviewer agreement is not acceptance. The known browser
observation remains negative transport evidence; the independent runtime priority diagnostic proves
current identifier coupling only. No new application, production deployment, package installation,
paid model call or human-use pass was performed for r4. See
[F1/F2 decision history](../../whiteboard/discussions/implementation/production-frontend.md).
