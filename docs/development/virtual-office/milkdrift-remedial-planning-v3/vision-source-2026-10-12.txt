5. Since we've established that a daemon can be used as an execution host to execute commands, setup a server environment and much more, with podman integration I'd want to continue with this idea. But I think the way we've been thinking about this requires very strong corrections and further definition of what a daemon is.

   Forget about combining workflows across daemons and using externally defined method workflows. A workflow should only be daemon specific and the daemon is the one that's in charge of the persistance and execution of a workflow, not some external frontend. That would be a chaotic scene of state and persistance management. This would also fully decouple the frontend. So we would be able to execute a workflow from a phone, close the app and still have it executing the workflow as it's decoupled. It also makes synchronization across devices incredibly simple as the daemon is the single source of truth of which the frontend would just simply fetch its state from.

   &#x20;&#x20;

   Daemons can advertise themselves to be an execution environment, but this is completely separate from that of our workflow execution and management. There's no relation. It's simply just the daemon providing an environment for executing commands. Anyone (if connected) can see and use this daemon in their workflow. It's completely unrelated if that daemon is on another host, or is the host itself and which workflow uses it (it's a completely different domain. This is not a cross-daemon workflow. It is simply just a workflow using a remote tool). The management of this environment should also just be the responsibility of the workflow itself, rather than the daemon providing the environment. By responsibility, I mean that the workflow is in charge of doing its own documentation of the server environment and execution, whether this will be in a project .md file or in the environment itself is up to the workflow using it. We shouldn't spend time developing tools, that could've just been easily defined by the workflow itself. It's the workflow's responsibility to document its usage and state. The beauty is that this remains the agent's task, and is completely decoupled and outside the scope of our project to handle. The project just offers the tools of creating tasks/operations with generalized behavior and structure. It's up to the agent to execute and define those behaviors and structures (or a human operator). Though it's probably good to clarify that the workflow owns the purpose, procedures and documentation of its environment. The execution host enforces the access and limits it actually offers.

   Also since the workflow is daemon specific, we'd have it structured as such in our frontends, so that we can easily see what daemon the workflow is residing and executing from.

   The only reason we made the old complex cross daemon and workflow blend, was mostly just to derive execution surfaces across daemons. We didn't establish that it was a different domain and made it highly dependent on workflows, which resulted in a complex blend of domains.&#x20;

   Now we've identified it as it's own domain, which has resulted in becoming just a general/generic execution surface rather than embedded in complex cross workflows and workflow methods... Any workflow can just simply call and use the advertised execution environment.&#x20;

   I guess I'll have to clarify how we can make this connection between daemon to daemon and how to make it secure (to be adviced this is going into a tangent and could be a faulty implementation, but simply serves as a guide)... We probably already have this defined, but the purpose is to link the daemons together in a peer to peer network using ssh and a LAN or mesh network which is up to the user to define and is outside of the project scope (as is desired). Now how would a user establish this link up? And how would the link up happen? I would think that the user would first link the daemons to their frontend. The daemons would then be able to see each other and asks the user if they should establish a peer to peer connection to execute commands and have independent persisted connection if accepted and authorized (which should be possible to configure from the frontend itself).

   Once daemons have been connected, they'll each save this connection into a table, so when another frontend interface adds one of these daemons (or may already have one added, but not the new daemon connected), they'll automatically get synced up with the new daemon. This makes sense since workflows are syncronized and the daemon is the source of truth. If it trust another daemon, then the frontend is expected to trust this as well. It would also make some ugly visualizations of workflows if the frontend wasn't aware of the execution environment a daemon is using, since it would be asynchronous (daemon is aware of another daemon and executes commands in the trusted environment, but the frontend is not creating unsyncronized behavior). It's expected that the frontend has the same amount of permissions as the daemon has to it's connected peers, since the daemon is the functioning entity and the frontend is only a visual wrapper. That's why it's important that daemons are clearly defined and segregated on the frontend to avoid confusion of permission structures, workflows and daemon settings when going back and forth between daemons and their setup/configuration.

I think I need to define some new information of method workflows.

You already know this, but a workflow method is just used to define instances of workflows that you want repeated. It gives you the ability to create your own custom instructions that agents can use to apply specific preferences or force a run through of a specific set of operations/tasks/instructions to produce a certain form of output.&#x20;

I imagine that these methods are available globally and can be used across various workflows to set enable specific preferences and standards rather than letting an agent go rogue. It's like planting little seeds to produce a certain outcome and quality.

The workflow methods are able to actively be mutated, as long as they aren't undergoing execution or have already been executed. Once an operation/task has been executed, it should be fixed on that timeline and be immutable (readonly).

The way that I see this working is that a workflow method within a workflow isn't defined until execution. The workflow method is just defined as a usual operation/task with a reference to the workflow method. Once it runs, it'll then materialize the method into it's corresponding operations/tasks that method currently is made up with. Though possibly with the operations/tasks marked with a tag referencing the workflow method it's derived from, so that we can see the operations/tasks are derived from a method as the materialization of the method are just baked into normal operations/tasks (which happens on execution). That way we avoid handling complex state changes and versioning as the methods just turns into whatever operations/tasks they're defining at the current moment at execution and we are able to view them in our timeline as a normal operation/task (though with a tag of origin). The only complexity we'd need is that we can't delete a method workflow as long as it's being referenced by targets that hasn't reached execution (is scheduled for execution in a workflow). Otherwise a workflow might become invalid. This is why the definition of a workflow method is initially just a normal operation/task, as an agent could serve as a guard to ensure a workflow method materializes and do a status report or other sets of operations like stopping the execution of a workflow due to errors or cancelling the execution of the workflow method to pursuit a different path. The beauty is that we don't define the workflow method until it's been executed, but simply just references it to be materialized, meaning that we can update the workflow method as much as we want without worrying about updating every single flow that references the method. It isn't defined until materialization, so the workflow method functions as the single source of truth until it's been materialized.

Now the question is what would this workflow operation/task look like? How would it materialize? And how would we want to map out our data structures? We know that we'd need a tag to reference the method (likely the method name along with a number for uniqueness and small versioning).&#x20;
