## Let the user perform the connected work

Provide a working built Svelte client and isolated authorized daemon roots A/B. Present the source
commit, startup URLs, finite grants and model/tool settings plainly. Use the retained production UI,
not a mock or a parallel test frontend. Configure a real permitted model for the useful journey when
available; use explicitly labeled controlled responses for repeatable fault branches. Never hide
real model failures behind a fixture-generated success. If access or spending is missing, prepare
all authorized review work and record the exact needed input rather than claiming a completed review.

Have the user submit the Rust learned-animation brief and inspect how planning creates three research
tasks, how parallel execution and a failed research input are represented, and how composition adds
corrective work and project setup. Let the user edit the shared setup template before activation,
then inspect and adapt a materialized future task. A review should add a linked correction and
continue automatically under granted limits. Ask the user to explain what they expect to happen next
and use that comparison to find behavioral confusion.

Run the integrated interruption branches from the journey: restart during accepted expansion; lose
a remote command response after entry; inspect uncertainty and safe recovery; request cancellation
without assuming it has stopped. The user administers the persisted A→B connection through the
supported flow and sees its state after A restart. They can distinguish A administration, B
administration and ordinary use. Do not change an unrelated running host or destroy real data to
stage a fault; fixtures/new roots supply controlled faults.

Close the phone/client, use a fresh authenticated session with no saved workflow ID or recovery file,
find the same work and an earlier result, then switch daemons. Show retention settings, explain
expired versus protected content, and inspect why unresolved work survives. A real device observation
and a phone-sized desktop viewport are recorded differently.

Run the timetable CLI brief with the same method: different folders, inputs and purpose must work
without editing product source. Review useful output and project Markdown/Git conventions as ordinary
files. Evaluate whether the method actually reduces repeated authoring while preserving desired
adaptability. Neither reusable code nor a fixture assertion alone establishes that user outcome.

## Repair and verify

Record concrete feedback, actual reviewer participation, model/tool environment, source and limits
in the single handoff and canonical evidence. Use ignored logs/screenshots for detail. Fix missing
backend behavior, confusing authority/connection steps, unreliable search, stale state, blocked-input
repair, inappropriate defaults and accessibility issues in this assignment. Product behavior can
change on observed evidence; update the ADR and all affected producers/consumers if it does.

Commit coherent tested repairs. Run affected Rust suites plus frontend check/lint/unit/build and
browser tests. Recheck the corrected connected segment with the user when required to establish their
feedback was addressed. Run documentation contracts/diff checks, and keep reference/status/operator
instructions accurate. Do not leave known in-scope findings to 07, but do not repeat the workspace
full gate here. It is owned by 07; CI remains strict.

If the user has not participated or a required behavior remains broken, leave 06 pending with exact
resume instructions. When the actual review and repairs are complete, report its tested commit,
what the user could do, concrete limitations and final acceptance prerequisites. Stop ready for 07;
no additional product subsystem or automatic successor follows from this checkpoint.
