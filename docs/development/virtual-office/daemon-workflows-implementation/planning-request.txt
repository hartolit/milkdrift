## The product to build

### Daemon-owned workflows and an independent Svelte client

Each workflow belongs to one daemon. That daemon stores its tasks and results, runs the work, accepts changes and reports progress. Closing a phone or desktop client must not stop execution. Another authorized client can reconnect and discover the same work without possessing a local recovery file or already knowing its ID.

**Svelte remains the first GUI.** It is a standalone client that can connect to several daemons and keeps their workflows, settings and permissions clearly separated. It uses public daemon operations, not CLI subprocesses, database access or its own execution rules.

### Ordinary tasks, with inputs supplied later

A task combines behavioral instructions with input bindings. The instructions can be written before the eventual input exists. Inputs may include text, files or earlier results. Tasks select configured models and permitted tools; Milkdrift does not perform inference itself.

Research, splitting assignments, criticism and composition should normally be uses of the same task model—not separate specialized products. A splitter can ask a model to produce assignments. The daemon checks and creates the requested tasks. A compositor is an ordinary task that receives selected results and reasons over them.

Instructions describe the work. Explicit dependencies tell the daemon when it can run. Do not let prose, screen position or timestamps secretly determine scheduling. Decide how missing and failed inputs affect readiness, and give the user a clear way to continue or repair.

### A workflow can grow as it runs

An agent can begin with a partial plan, examine results, add work and revise tasks that have not started. Users have the same supported editing path. Work may continue through criticism and correction without a person manually launching every next round, within the access and limits the user has granted. Specify when it finishes, waits for user input, or stops because of repeated failure or exhausted limits.

Freeze the instructions and inputs actually used once a task starts. Its progress and status can still change. A correction is new or revised future work, not a rewrite of an earlier execution. Decide how a running task is stopped or replaced without pretending a cancellation request proves it stopped.

### Methods are reusable templates, expanded locally

Methods reduce repeated authoring and let users encode preferred procedures. They are available across workflows, not restricted to one project. A template’s owner can edit it; consumers cannot alter the shared template merely by using it.

A queued method use refers to a template. **When that use activates, expand the current saved template into ordinary tasks in the owning workflow.** Record which template content produced that expansion. Later template edits affect future expansions, not existing copies. Materialized future tasks can be adapted like other future work.

This is neither a remote workflow service nor a permanently linked child run. Do not replace it with definition-time pinning or force every use into a separate workflow.

Prevent deletion of a method while queued references still require it, unless those references are deliberately removed or replaced. Settle incompatible input changes, naming/identity, nested references and interrupted expansion. Expansion must not insert tasks twice or change its selected template after an interrupted accepted expansion.

Pick the simplest library arrangement that provides cross-workflow reuse. Explain sharing between daemons without introducing remote workflow ownership or an unnecessary central service. Retain enough origin information to inspect a copied task; do not recreate the old versioning hierarchy merely for this.

### Remote environments are tools

Keep the execution-host and Podman direction. A workflow can use an advertised local or remote environment to run commands and set up services. Its own daemon remains the workflow owner. Remote hosts enforce their offered access and limits and report the operations they execute.

The workflow maintains project-specific procedures, environment explanations and documentation through ordinary files and tools. Milkdrift need not implement a specialized documentation, deployment or knowledge product for those tasks. It still must know enough operational state to avoid treating a lost connection as proof that a command never ran.

Store configured execution-host connections on the daemon, so its authorized clients see the same available tools and reported state. The GUI must support connection administration without requiring each client to rediscover the topology. Seeing a remote host through daemon A must not automatically distribute credentials or grant direct administration of that host. Choose a secure, straightforward connection flow; the operator supplies LAN/mesh connectivity. The earlier SSH suggestion is not a requirement to invent a new transport.

### A useful timeline, not a permanent knowledge system

Show work from left to right with titles, short descriptions, actual start/end times and clear queued, running, completed, failed and stopped states. Explain parallel work and dependencies. Method-derived tasks show their origin; follow-up work links to what it addresses.

Humans and agents can search and browse recent tasks and inspect their results without being given exact IDs. Keep this on the selected daemon’s authorized public path.

Use configurable rolling retention for completed history and context. Do not discard unfinished work, unresolved remote operations or inputs still required by pending tasks simply because they are old. Explain what expires and what remains protected while needed.

**Project knowledge lives primarily in ordinary Markdown files and Git.** Agents maintain architecture, rules and practices as part of their work. The product does not need permanent forensic history, a specialized lesson database, mandatory evaluated learning or a documentation interface. Git does not replace the minimal state needed to manage running operations.
