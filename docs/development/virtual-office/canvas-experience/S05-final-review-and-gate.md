## Observe useful reuse and repair findings

Have the requesting user continue on the maintained production client. Start from useful work,
select a clean procedure, save it as a method and use it for a different question/project with
recognizable inputs. Also author a small method from scratch. The user should explain what the
method takes, what it returns, which shared content may still change, and whether their edit changes
one use or the library. Observe hesitation and wrong expectations, not just successful clicks.

Include a delayed use whose template changes, a missing/incompatible input repaired at the endpoint,
an expanded copy with a genuinely queued task that can be changed, and a result available to inspect
before its downstream release condition. Show a successful negative critique without a false approval
badge. A completed coding run with a later improvement must preserve its actual history. Check that
the method removes repeated authoring without requiring internal IDs or a configuration tutorial.

Repeat the core tree, blank placement, right inspector and direct connection journey with keyboard
and narrow-screen controls. Reconnect to unfinished work and inspect output while another task runs.
Use the real logo and selected visual direction. Record actual device/browser, configured model/tool,
brief, useful output and limits. Controlled-model plumbing is not real-model quality. At least one
early user-reviewed task must already have useful input-dependent output rather than only canned
content, as required by main 02. Do not invent paid-model access or user participation.

Fix observed flow and behavior problems with the owning implementation and update affected decisions,
consumers and evidence. Recheck material repairs with the user. If participation is unavailable or
the method does not fulfill its promised journey, leave this acceptance pending with exact resume
instructions; passing automation cannot close it.
