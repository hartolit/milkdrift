## Result and ownership

Blueprint owns a digest-bound agreement outside the editable task region. Its fingerprint preserves
workflow/package identity, interface, metadata, enclosing nodes and every incident boundary edge.
Only ordinary tasks with exact declared capability requirements fit the editable prefix. Node and
cumulative revision ceilings are explicit. This permits useful investigation, replacement and internal
dependency edits without inferring equivalence of arbitrary programs.

Runtime accepts the binding before start, inherits the original binding into structured children,
rejects independent governed child adoption and retains the cumulative adoption count through replay
and snapshots. Control classifies qualifying future changes under `milkdrift.agreement-adaptation`
version 1; generic risk policy and explicit requested-approval behavior remain unchanged. Active
adoption cannot replace the agreement. A legitimate requirement change uses a separate agreement,
installation and run, preserving original failed evidence. No administrative deviation is supported.

Authority owns the finite protected effect policy. Workspace owns the exact candidate/observation
contract, and the artifact store owns immutable bytes. Capability-host owns trusted evaluation and
publication; redb owns its immutable request receipts, incomplete/completed evaluations and durable
managed transitions. The Linux adapter performs the fixed verifier and systemd/Podman mechanism.
No alternate scheduler, provider family, raw engine interface or general semantic scanner was added.

## Effect and evidence boundary

An evaluation binds the artifact's identity/digest/size/media type, agreement, recipe/configuration,
policy, trusted producer/verifier, target generation and validity interval. Artifact read authority
and sensitivity are checked before content inspection. Verifier code, native interpreter and test
credential are operator-pinned outside worker mounts. Uploaded reports can select an evaluation
identity but cannot populate its trusted private record. Missing, failed, unknown, expired, different
or revoked evidence cannot publish. The table refuses at 4096 retained evaluations; failures and
replay records are not evicted. Interrupted evaluation does not rerun on exact replay.
Each accepted evaluation owns its scratch directory and labeled test container. A distinct authorized
request can renew verification of unchanged bytes at the same target generation without replacing an
earlier observation. The Linux owner fences detached verifier containers after completion or timeout,
and on startup after interruption. Cleanup failure cannot produce passing evidence.

Publication reads the checked artifact bytes, prepares an immutable file and accepts generation N+1
only for evidence bound to N. It records the intended transition and authorization before changing
the service, then rechecks authority/policy/expiry and candidate-file bytes at configuration/start. A raw update cannot replace
protection or candidate; raw start requires accepted evidence. The protected installation exposes no
worker, served-content write path, engine socket or arbitrary host process. The separate worker has
only its approved `/workspace` and bounded stdout artifact export.

The accepted receipt and current inspection are deliberately separate. A lost response or failed
terminal report retains the intended effect or uncertainty. Exact replay returns the original receipt,
and authorized recovery resumes only the exact saved intent. A workflow-origin request cannot be
replayed as a direct request with different authority provenance. A running systemd service may restart
its accepted generation with retained data; evidence expiration blocks new controlled entry rather
than retroactively withdrawing an already deployed service.
Known managed refusals without an accepted intent produce a terminal rejection with no effect. A
failure after an accepted intent retains uncertainty, including a completed service change followed
by failed capability-registry reporting.

## Public use and finite example

[The maintained example](../../../../../examples/adaptive-slotbook/README.md) fixes the HTTP/API
before candidate construction and authors complete files through production CLI readers. `prepare.py`
uses local `artifact digest`, `blueprint effect-policy`, `blueprint create` and `blueprint govern`.
`qualify.py` uses authenticated resource, artifact, invocation, proposal and run commands against actual
binaries. No Rust harness is needed to author a working proposal or execute the repair.

The version-1 strict proposal `draft` derives canonical mutation/proposal identities before ordinary
admission. Unknown/duplicate/mixed envelopes refuse. The same reader is consumed by the existing
workflow-control proposal operation. `resource evaluate/evidence/publish` and the selected-input
`resource.evaluate_candidate`/`resource.publish_candidate` operations share one owner. Run inspection
shows the accepted origin and cumulative adoption count; target inspection shows `accepted_evaluation`
for candidate/check inspection. CLI request timeout now follows the explicitly selected command
budget, while the existing overall deadline still bounds the whole command. `invocation prepare`
validates the saved request and supplies a stable key for idempotent-write operations. The example
retains artifact observations across progress pages and refreshes discovery only after an explicit
stale-catalog refusal with no accepted execution.

The seeded anonymous/in-memory application and repaired SQLite application are deterministic fixtures,
not model output. The verifier checks public availability, authenticated mutation, capacity/intervals,
restart persistence, cancellation cutoff and exact deployment. It recreates its private container with
retained data, matching the managed service lifecycle. Python source and the immutable runtime image
are the build output; there is no rebuild from a mutable checkout after checking. The clock is an
explicitly variable operator-controlled input. The native Python standard library and OS remain
trusted prerequisites; executable/source hashes do not claim a hermetic trusted host.
