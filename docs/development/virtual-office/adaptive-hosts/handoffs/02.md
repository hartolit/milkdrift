## Product path and owners

The production daemon composes `ManagedResources`, the redb resource port, a registry projection,
and `LinuxManagedPlatform`. Both host roles support managed workers and optional model endpoints.
The CLI/client `POST /v1/resources` path and the ordinary `milkdrift.resources` capability invoke
that same semantic owner. Inner authority checks select the installation and exact operation,
retain originating scope, and authorize the resulting platform requirements below either transport.

The [operator guide](../../../../operations/managed-linux.md) owns exact bootstrap, resource,
worker invocation, inspection, recovery and removal commands. The normal binary provides
`managed-bootstrap --preview` and repeatable private configuration creation. The
[maintained inputs](../../../../../examples/managed-linux/README.md) use the single Slotbook brief.
Bootstrap needs no model and performs no elevated package, account, firewall, VPN or service setup.
The supplied worker image digest is deliberately a placeholder: an operator must approve and
preload real exact tool/server inputs before apply can pass prerequisites.

Portable request/inspection and descriptor bindings belong to `capability::managed`;
`persistence::managed` owns the durable records and transactional ports;
`capability_host::managed` owns lifecycle decisions and its ordinary adapter. The Linux crate owns
bounded helper commands, strict recipes, generated Quadlets, rootless workers and the managed model
wrapper. It reuses the existing provider implementation and its frozen preparation; the core owns
no inference. [Architecture](../../../../architecture.md) and [ADR 0039](../../../../decisions/0039-managed-resource-ownership.md)
are the canonical design owners.

## Transaction and recovery boundary

An exact actor/command key binds the complete managed request and accepted grant to an immutable
receipt. Replay reauthorizes disclosure, returns that original receipt, and executes no platform
call. The receipt can still say pending after successful completion; inspection projects the latest
inventory. Expected versions cover use changes as well as lifecycle changes. Removed names remain
tombstones. An incompatible reapply requires explicit update and interruption authorization.
Receipt transactions repeat the exact grant and originating-scope comparison so simultaneous
callers cannot bypass that binding between lookup and commit. Recovery authorizes the saved pending
candidate, including replacement resources that differ from the old approved setup.

Redb atomically commits installation intent, closes admission and checks all relevant lifetime
holds. Local `CapabilityResolved`/`NodeScheduled` acceptance and serving admission acquire exact
managed-generation dependencies in their existing acceptance transaction. Entry decisions and
terminal observations update those same holds. There is no resource-side duplicate runtime or
lease-expiry inference that entered work stopped.

Editing and lifetime protection are separate. One mutating use per working area is initially
allowed. All requirements acquire coherently or refuse immediately. A child can reserve lifetime
protection only against the exact authoritative `SubworkflowCreated` association and inherited
execution basis. Handoff requires physical parent quiescence, installation version, both claims,
generation and association. Parent editing suspends while both lifetime holds remain. Return
requires child quiescence; parent resumption additionally requires current authority and an
uncancelled execution. Claims advance, so old callbacks cannot enter. A cancelled parent may settle
without regaining editing. Tests include an independent model-resource reader progressing while
child mutation excludes conflicting writers and maintenance.

02 exposes these resource transactions. 04 still owns the published invocation/run association
and integrated single-worker composition. It must use the real accepted relationship, not a shared
actor/workspace name, and must not treat an acknowledgement or timeout as physical stop evidence.

One bounded driver per installation prevents concurrent command copies from repeating platform
steps after sharing an acceptance receipt. Inspect remains available and saved receipts replay
without joining the driver. The concurrency regression detects a deliberately disabled guard.

Platform identity and exact configuration are saved before effects. Names and ownership labels bind
the machine, account and manager root as well as the installation token; a second manager with
identical actor/grant/request inputs cannot adopt the first manager's resources. Service start checks
existing labels before invoking systemd and explicitly disables Podman's default replacement.
An owned systemd drop-in also replaces generator cleanup with exact container-ID commands; a
failed supervisor start cannot remove a foreign name collision. Effective cleanup is checked after
reload and before use. Linux mechanism version 2 binds both configuration directories into approved
deployment state; the prior mechanism is not silently adopted. Each finite step checks its recorded identity, then commits observed evidence with transition/index guards. Pending steps can
resume after restart. Recorded uncertainty requires explicit recovery of the unchanged intent.
Interrupted publication rebuilds from verified inventory without repeating platform changes.
Failed replacement keeps the old approved generation and the unverified candidate visible, with
admission closed. There is no database/platform atomicity or automatic data rollback claim.

Authorized blocker resolution first commits a newer fencing claim. Linux waits for local creators
under a finite deadline and proves absence of the exact task, or stops the exact owned model
service. An attached endpoint is never stopped. Reclamation changes resource eligibility; it does
not manufacture a terminal result for the old execution. Entered uncertainty survives serving
observation compaction. Integrity checks bind archived identities and descriptor digests to their
retained generation and resource dependencies.

## Recipe, protection and retained data

The implemented mechanism targets rootless Podman 5.4 through 6.x, systemd user services and cgroup
v2. It validates installed prerequisites and generated definitions rather than accepting raw engine
or unit text. Worker rootfs is read-only, capabilities are dropped, no-new-privileges/seccomp and
private UID/GID mappings apply (two 65,536-ID ranges for a worker beside an owned model), and one owned working volume plus bounded temporary storage is
writable. Effective image, mounts, device exposure, memory/swap, CPU and PID limits are checked.
The probe runs real tools and checks kernel limits and denied rootfs/manager access before publishing.
Outbound networking is an explicit unrestricted-destination choice; it is not destination isolation.

Git/Rust/C tooling comes from an operator-approved exact image. Mutable tools under the workspace
remain experiments until explicitly promoted to a new image. Working files and knowledge survive
identical reapply, as do staging/data volumes. An owned llama-server receives exact shared read-only
weights, a loopback port and declared CPU or Vulkan backend. Its service lifetime belongs to systemd,
not an invocation. Recipes supply explicit provider token/billing contracts so prepared calls pass
ordinary serving admission without weakening its unknown-resource refusal. These declarations require
operator evidence; the supplied endpoints do not establish tokenizer or output enforcement. Owned
verification includes bounded inference; Vulkan also requires observed nonzero offload evidence.
CPU success supplies no GPU or throughput evidence.

Manager state, credentials, definitions and engine/systemd controls remain outside worker mounts.
The manager account and native profiles remain trusted. There is no claim to contain arbitrary
native code running with that same host identity.

Removal uses the saved preservation decision and exact ownership; it does not prune globally.
Shared images/toolchains/weights and attached services cannot be deleted by this lifecycle.
Inventory, receipts, exact generated configuration and unresolved relationships survive a store
backup. Volumes/images, external model files, credentials, host Quadlet files and attached-service
data require separate backups. Restored stores retain inspection-only execution guards; a second
manager cannot lock the same root. No clone-activation/adoption procedure is supported.

Inventory bounds are 1,024 names including tombstones, 16 resources, 128 unresolved uses per
installation and 16 transition steps. Historical receipts and transition evidence retain exact
replay and consume disk. Startup scans bounded live state; historical integrity uses bounded pages.
