# 05 — Learn reusable methods and produce isolated variations

## Assignment and dependency

After 04 is accepted, implement one complete path from experience to an evaluated reusable method
and product variations. Read accepted handoffs 00–04, [the sprint README](README.md),
[the discussion](discussed-direction.md), and [AGENTS.md](../../../../AGENTS.md). Apply
[implementation practice](../../practices/implementation.md),
[documentation practice](../../practices/documentation.md), and the
[verification policy](../../workflow.md).

An authorized agent must select relevant run evidence, propose an improved blueprint, evaluate the
candidate on distinct inputs, and promote or reject it through ordinary control/publication. The
promoted method must be reusable for independently tracked product variations. This is not a claim
of guaranteed self-improvement and not a new LLM memory engine. It is a usable, auditable learning
workflow with explicit inputs, criteria, authority, and outcomes.

Use [Slotbook's maintained specification](../../../guides/adaptive-method-example.md) and actual
source evidence from 03–04. It owns the four separate evaluation inputs, loan/class variations,
unchanged verifier, fixed two-round improvement threshold and rejection/inconclusive rules. Do
not invent another application, leak evaluation cases into the proposal context, or retune the
criterion after observing a preferred candidate. Record the exact evaluation declaration before
proposal generation and preserve seeded versus observed-model evidence as different lanes.

## Existing owners to use

Trace bounded causal context and historical artifact discovery; workspace scope/value ownership;
control proposal, approval, and prospective adoption; immutable blueprint/mutation construction;
controller repetition and cumulative accounts; the protected method agreement from 03; publication
and invocation from 04; and managed working areas/recipes from 02. Use the ordinary model and process
adapters and supported structured-output validation. Search for existing APIs that express the
needed behavior before adding a new contract.

Prefer maintained ordinary workflows, small typed proposal/evaluation contracts where missing, and
existing bounded query owners. Do not create a parallel lesson database, generic prompt-history
store, ECS/vector search subsystem, new scheduler, or fine-tuning service. A discovered missing
selection or publication API belongs to its existing owner and all consumers must adopt it.

## Required implementation

### 1. Selected knowledge with source and scope

Give each managed working setup a discoverable documentation/knowledge entry point: purpose,
operating instructions, relevant decisions, known limitations, and approved learned guidance. Use
ordinary files for editable working documentation, and existing immutable artifacts/scoped values
for selected evidence and exact versions. Do not make a mutable wiki the historical truth of a run.

Implement the supported update/select/inspect path through authorized product operations. Record
source runs/artifacts, applicable method/version/workspace, supersession, and relevant approval or
promotion identity. Latest useful guidance may change; each task's selection freezes the actual
version it received. Updating knowledge must not rewrite completed context or apply as an invisible
instruction to already prepared work.

Cross-run learning is explicit, bounded, and authorized. Select the exact permitted runs/artifacts
and projection pages; do not scan all historical content or bypass branch/sensitivity restrictions
under a “learning” role. Distinguish access to a public result from access to private internal
publication history. Unknown/missing/denied evidence is explicit and cannot be represented as absent
failures. Retrieved text and model output remain untrusted data, not a new grant or governing policy.

Do not automatically inject every new lesson into every active agent. Later selection or a scoped
prospective revision can incorporate it through existing context/control semantics. Automatic
subscription/global event distribution is not needed to finish this learning path.

### 2. Propose a method from evidence, not from a successful trace alone

Ship a maintained learning workflow that selects prior attempt/result/adaptation evidence and asks
an external model for a bounded structured candidate proposal. The example should address the user's
concrete concern: unclear planning produced contradictory implementation or avoidable repair.
Supply that problem and the permitted editable scope; let the agent propose an evidence-supported
method change. A requirements/planning responsibility is a hypothesis, not a mandated graph change,
prompt, node name or answer. The proposition must cite the source run's relevant decisions,
contradictions, failed checks and repair, and state expected benefit, applicability, unchanged
obligations, and what would count against it. A repaired application alone is insufficient evidence.

Parse the candidate through ordinary blueprint/mutation/control validators. A prose suggestion,
model confidence, successful earlier run, or a node renamed “planning” is not a validated method.
Keep existing version and agreement separate from the candidate. Retain failure/rejection evidence
rather than pruning inconvenient examples from the account of how the candidate was chosen.

The learning agent may be authorized to propose and evaluate without being authorized to change
published obligations or promote the result. Also support an explicitly preauthorized promotion
policy for declared criteria where the operator chooses it; human approval at every iteration is
not a universal requirement. Policy and authority must be external to the candidate being judged.

### 3. Execute a real evaluation path

Run the candidate on declared inputs separate from the source trace, with explicit baseline,
comparison criteria, output acceptance, and cost/time limits. Preserve exact method, agreement,
recipe/tool/model provenance and unknowns for both baseline and candidate. Measure concrete outcomes
such as required checks, contradictory-feature detection, unnecessary repair count, accepted outputs,
and attributable usage where observable. Do not infer causal superiority from a small sample or
invent model-quality scores.

A candidate that passes those tests becomes eligible for promotion under the declared policy; it
is not certified universally better. Failed or inconclusive evaluation remains a first-class result
and cannot automatically change the current method. Prevent the candidate or its agent from editing
the verifier, test inputs, comparison criteria, or promotion threshold while being evaluated.
Legitimate changes to the evaluation design require their own authorized new evaluation.

Use existing controller/repeat/adaptation paths for further iterations, with hard bounds and human
checkpoints where configured. A new run, revision, retry, failed evaluation, or restarted service
cannot reset the applicable cumulative account. Exercise stop-at-bound and continuation with
retained evidence. Do not introduce an uncontrolled background improvement loop.

### 4. Promote and reuse without silently changing existing calls

Promote an accepted candidate as a new reusable blueprint/publication version through 04's owner.
Bind the evaluation evidence and decision. Publication selects future work only; old versions,
already accepted invocations, active variants, and their obligations remain exact. Rejection, withdrawal,
retirement, and a failed promotion commit must preserve useful evidence and safe replay.

Support going from exploration to a callable method and then improving that method again. There is
no irreversible “static” state. The current invocation, reusable method, public agreement, and
selected publication are separate identities; an authorized edit must specify which it changes.

Use explicit version selection in examples. A mutable convenience alias may resolve to an exact
version before acceptance if already supported, but cannot silently change the version of accepted
work. Avoid adding a new alias subsystem merely for this assignment.

### 5. Product variations through ordinary workflow composition

Use the specified bounded variation inputs and execute independent loan and class variants of the
selected method. If evaluation rejects the candidate or is inconclusive, the retained baseline can supply these
variants; do not call that candidate promotion. They share the selected method and constraints but have
separate run identities, working areas/worktrees, inputs, artifacts, acceptance decisions, and
attributable usage. Use existing fork/subworkflow/peer placement mechanisms where appropriate.

Variant generation must create meaningfully different outputs under the same method, not simply
copy one completed artifact and change its label. Retain each result, why it was accepted, and its
parameter/method lineage. Provide an operator comparison and explicit selection path; selection
must not rewrite losing variants or silently deploy all of them. A variant's protected publication
still requires its own current applicable evidence and target authority.

Mutating variants cannot share the same checkout. Enforce resource holds from 02 and context
visibility from existing owners; allow shared immutable inputs where authorized. Merging selected
work requires an explicit operation. A failed/uncertain variant must not publish another variant's
result or release unrelated usage.

### 6. Connect maintained setup improvement to the same rules

Show that an agent can experiment with a tool within the prepared workspace, then propose a recorded
recipe/configuration change for maintained use. Verify that change in a fresh owned setup or staged
generation before activation, preserving working data. The method/recipe relationship must be
inspectable: a blueprint does not silently inherit unrecorded tool changes, and a recipe update does
not silently promote a different workflow method.

Use the existing managed lifecycle and publication mechanisms, not a second installer. Approval and
verification protect the manager/permissions; the worker cannot gain authority by editing a recipe.
Recorded scripts and package locks may be recipe inputs, but copying mutable container state without
capturing dependencies is not a reproducibility claim. Be explicit about unavailable upstream inputs,
mutable external services, and data that requires backup rather than reinstallation.

### 7. Complete operator and agent access

Provide maintained workflow/example documents, production-reader validation, client/API/CLI entry
points for the missing operations, bounded progress/result inspection, candidate comparison,
promotion/rejection, and variant selection. These paths must be usable without editing a private
fixture or opening redb. Agents use the same grant and proposal paths as human clients.

Use the available local model through existing supported profiles; a paid provider or a new provider
family is not required. Deterministic model fixtures prove validation and refusal behavior. The
actual local model demonstration in 06 must use this same learning workflow and return a real
structured candidate, not an example proposal substituted by the evidence harness.

## Required tests and demonstrations

Prove each positive path and its meaningful counterexample:

- Select authorized earlier evidence and reject cross-workspace/private-history leakage; updated
  knowledge changes future selection while past manifests remain exact across restart.
- A model-produced structured proposal creates a genuine candidate blueprint with evidence linkage;
  malformed output, invented evidence, forbidden edits, or altered obligations is refused.
- Evaluate a useful candidate on distinct inputs with real verifiers. A failing/inconclusive candidate
  remains unpromoted. Candidate edits to test criteria or evaluator configuration cannot game promotion.
- Automatic promotion succeeds only under its separate exact policy/grant; invoke/propose-only actors
  cannot publish. Explicit human-reviewed promotion uses the same control and evidence owner.
- Restart during evaluation or promotion and replay the command: no duplicated runs/publication and
  no reset of the evaluation/controller allowance. Unknown costs or effects remain unresolved.
- Execute at least two actual product variants with independent writable state and preserved shared
  method identity. Verify evidence isolation, selection, and protected deployment of only the chosen
  candidate under the correct target policy.
- Promote a newer method while an older published invocation is active: the older call retains its
  selected agreement and allowed adaptation. Rejected candidates and prior evidence remain inspectable.
- Change scratch tools, produce a recipe candidate, recreate/verify the maintained tool setup, and
  preserve working data. Reject an attempted permission/manager-access expansion in that change.

Run the full gate plus relevant context/control/blueprint/runtime/authority/daemon/publication/resource
suites and actual-binary deterministic scenarios. Retain raw model requests/responses only under
applicable sensitivity/retention policies. Report test scope and uncertainty, not universal learning
quality. If a model happens to choose an unhelpful method, keep that evidence and evaluate honestly;
do not alter criteria or fabricate a success to complete the sprint.

## Completion and handoff

The stop condition is one complete evidence-to-proposal-to-evaluation-to-promotion/rejection-to-variant
path, built from ordinary workflows and existing owners, with useful CLI/API access. A documentation
page promising later learning, an unused knowledge schema, or hand-authored fake model improvement
does not meet the outcome. Fix missing core adoption/context/ownership behavior in this scope now.

Update guides, maintained examples, parser/reader checks, architecture and exact implementation
status. Write `handoffs/05.md` with selected evidence semantics, candidate/evaluation/promotion owners,
version and recipe relationships, tested variants, actual commands and results, and remaining real
model/physical qualification. Do not predeclare 06's operational review passed.
