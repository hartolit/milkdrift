## Planned product successor — not ratified

Workflow/workspace/authority is the next direction, not an active phase. A future
ratification must define:

1. versioned workflow, node, port, artifact, workspace, authority, capability,
   budget, and execution-endpoint schemas;
2. package roles for a portable SDK, workflow runtime, provider adapter, plugin,
   headless host, and tools;
3. a minimal general workflow runtime and headless host;
4. durable run/workspace provenance and explicit commit authority; and
5. a coarse provider/peer endpoint contract that does not pretend remote work has
   E0's local native ownership.

Durable context search, recursive runs, capability-scoped plugins, provider/peer
targets, and a visual control center remain inactive tracks.

## Operating rules

- Start from a reviewed clean tree and keep generated artifacts in approved
  isolated targets.
- Preserve exclusive ownership, bounded work, no silent fallback, portable domain
  targets, backend-neutral E0, frontend-neutral E1, and thin hosts.
- Keep correctness, hardware, performance, process sampling, whole-device
  sampling, and CI infrastructure as separate evidence classes.
- Record decisions in ADRs, current behavior in project reference, support and
  historical accepted runs in status, procedures in validation, measurements in
  performance, and chronology in history.
- Do not activate the product successor until independent source closure and the
  external exact-commit acceptance condition are satisfied and a separate decision
  ratifies it.
